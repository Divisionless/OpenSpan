## What the service owns

1. **Feature registry** — register features with id, title, section,
   default-enabled, and their default shortcuts. Query and set enablement
   through the config store (config is the truth; the registry supplies
   defaults).
2. **Settings access** — typed get/set per feature, delegating to the
   store, with the feature's declared default as fallback.
3. **Reset** — per-feature and global, both landing in the store.
4. **Import/export** — delegate to the store, but validate first and
   report problems as a list rather than raising past the caller.
5. **Shortcut collisions** — the real value here. Given the registry's
   defaults plus user overrides, compute every conflict: two commands
   claiming the same chord, and a chord that is a strict prefix of a
   sequence. Use the landed chord parser so canonicalization matches the
   router exactly ("Win+Shift+S" and "win+shift+s" are one chord).
6. **Hook disclosure** — a plain report of which registered features
   request input hooks, for the honesty page the old program shows.

## Decisions already made

- The service holds NO Windows state and installs nothing; it is pure
  orchestration over the store and the registry.
- Everything is constructor-injected (`ConfigStore` instance in, registry
  in) so tests never touch the real product root.
- Section names come from the old program's four sections; keep them.
