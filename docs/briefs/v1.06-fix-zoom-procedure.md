# Brief v1.06-fix — Zoom must use the old app's actual procedure

Doug tested the shipped zoom: "it zooms all pages but also, upon first
tick, shifts everything to the right all at once." He is right, and the
cause is identified — two functions the C# depends on were not ported.

Fix `win/screen_zoom.py` and `win/test_screen_zoom.py` only.

## What is missing (verified by diff against the reference)

`D:\EsotericOS_Antigrav\src\EsotericOS.Core\Appearance\ZoomMath.cs` has
THREE viewport/level functions. The port has only the first:

1. `ViewportOffset` — ported. Centers the viewport on the anchor. In the
   C# this is used ONLY to establish a gesture's first frame.
2. **`RescaleAbout` — NOT PORTED.** Moves the viewport so the anchor stays
   on the same screen pixel while the level changes, *preserving any pan
   the user already has*. There are two overloads and the FLOATING-POINT
   one matters: a ramp feeds each result into the next call, and its own
   comment explains that rounding between steps does not cancel — the
   residue accumulates in one direction and the whole field slides toward
   the viewport corner. Keep the viewport fractional; round only when
   handing the rectangle to Windows.
3. **`EaseLevel` + `RampTimeConstantMs` (55.0) + `RampSettled` (0.005) —
   NOT PORTED.** The ramp eases in LOG space as a function of ELAPSED
   TIME, not frames, because each magnification call blocks until the
   compositor takes the frame. Read that comment in full; it records a
   measurement (a per-frame ease took 480 ms to settle one notch).

Applying a single instant `ViewportOffset` per notch — what the port does
today — is precisely the reported symptom.

## Implement the procedure, not just the functions

Port `ScreenZoomModule.ZoomAt` faithfully, including:
- gesture continuation: same display AND within the gesture gap keeps the
  ORIGINAL anchor; otherwise the anchor and monitor are re-established;
- `source = monitor under the pointer, else primary bounds`;
- unzoomed target resets everything;
- a ramp/render loop that advances `EaseLevel` toward the target and
  composes `RescaleAbout` in floating point each frame, applying the
  rounded rectangle to the magnifier.

**Multi-monitor correctness matters here and is likely a second bug.**
`MagSetFullscreenTransform` takes offsets relative to the PRIMARY
monitor's top-left in unmagnified coordinates. This machine's desk is
three displays with one at x = -1920 and another at y = -1080, i.e.
negative virtual coordinates. Work out what the API actually expects,
state your conclusion in a comment, and make the transform correct for a
pointer on a NON-primary, negative-origin monitor. A test must pin it.
